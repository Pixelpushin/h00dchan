# HOODCHAN Breeding System — Design Spec (v2)

**Status:** Approved (Brady, in conversation) — SUPERSEDES the v1 spec in full
**Date:** 2026-08-21 (revised 2026-08-22)
**Frontend home:** `fuck.hoodchan.org` (dedicated mini-app, same pattern as `brawl.`/`fight.`)

> **Supersession notice.** Two build attempts against the v1 spec were blocked
> by adversarial review, and the design has since been revised substantially,
> explicitly modeled on real, verified CryptoKitties contract mechanics. The
> following v1 sections are DEAD and must not be reintroduced:
> **commit/reveal seed hiding**, **dual-currency (ETH) payments**,
> **mint-into-TBA / nested baby ownership**, and **numeric-magnitude
> dominance genetics**. Everything else (project context, collections, art
> pipeline, CHAN wiring) carries forward.

## Goal

A CryptoKitties-style breeding loop across the HOODCHAN ecosystem's three
collections — HOODCHAN, Girlfriends, and Babies — producing a new baby NFT
whose traits are genuinely inherited from both parents, despite the source
collections having incompatible art/trait taxonomies. Must be robust, fun,
and rewarding: real genetics (not a reskin), a real P2P siring economy, and
payoffs that plug into systems that already exist (XP/leveling, the OpenAI
art pipeline) instead of bolting on new ones.

## Context (carried forward from v1, still true)

- **HOODCHAN** is live on Robinhood Chain (chain id 4663, `0x1237`) at
  `0x774Db2207D26570F5638028839c816702A40aBC2` (`lib/chain.ts`). Its traits
  live in off-chain ipfs:// metadata, so its 5-slot genes are synced on-chain
  by an operator script (`breeding-app/scripts/sync-genes.ts` +
  `BreedingController.setHoodchanGenesBatch`) — a documented trust point.
- **CHAN** (`0xB36fD5d3392C78E70c3E08f46b46F242e7EF654F`, 18 decimals, supply
  69,420,420,420) is already wired in as an access-gating token
  (`lib/holderAuth.ts`). Breeding fees reinforce it. CHAN is the ONLY fee
  currency (see "Cut from scope").
- **Art pipeline:** reuse the existing OpenAI image pipeline as-is —
  `lib/onlychansImage.ts`'s raw-fetch pattern (direct `fetch` to
  `/v1/images/generations`, no SDK, upload to Vercel Blob,
  `OPENAI_API_KEY` already configured). The breeding variant already exists
  as `breeding-app/lib/breedingImage.ts`; the five winning gene-slot values
  become a text prompt for a single blended "hood-meme baby" character. No
  pixel-layer compositing — the genome is what's real; the image depicts it.
- **Framing rule ("no literal infants"):** babies are rendered and described
  as freshly spawned, breeding-age-at-mint characters — meme-culture
  offspring, never child-coded imagery or wording. The `HoodchanBabies` /
  `HCBABY` contract name/symbol are the one allowed exception; all other
  on-chain strings, metadata, and art prompts stay in that register. This is
  reinforced (not weakened) by babies being immediately breedable (below).
- **Trait registry:** `breeding-app/lib/traitRegistry.ts` is the canonical
  trait-string → uint8 index registry (both directions), generated by
  `breeding-app/scripts/build-trait-registry.ts` from live HOODCHAN metadata.
  Its 5-slot collapse (Hats→hat, Faces→face, Bodies→body,
  Backgrounds→background, Extra/"Girl Stuff"→accessory; Grillz/Grills
  cosmetic-only) stays. Its ascending-rarity ORDERING is no longer
  load-bearing (coin-flip genetics is band-agnostic — see Genetics), but its
  reserved-band structure becomes load-bearing for mutations (see Genetics).

## Collections and the breedable allowlist

Three ERC-721 collections, all symmetric participants:

1. **HOODCHAN** — existing, untouched, external.
2. **HOODCHAN_GIRLFRIENDS** — dummy placeholder (~12 tokens,
   `breeding-app/contracts/src/HoodchanGirlfriends.sol`), address is config,
   swapped for the real collection when it ships. Already exposes
   `genesOf(uint256) returns (uint8[5])`.
3. **HOODCHAN_BABIES** — mint-on-breed only
   (`breeding-app/contracts/src/HoodchanBabies.sol`). Stores the packed
   genome + seed on-chain. **Rename its existing `genomeOf` to `genesOf`**
   so it satisfies the same interface as Girlfriends with no special case.

A single `mapping(address => bool) isBreedableCollection` allowlist in
`BreedingController` covers all three. Each allowlisted collection must
expose `ownerOf(uint256)` and `genesOf(uint256) returns (uint8[5])` in the
same shape. (HOODCHAN itself is fronted by the controller's synced
`hoodchanGenes` mapping via an adapter path, since its genes aren't readable
on-chain — implementation detail, the interface contract is what matters.)

**No collection is restricted to a role.** Any token from any allowlisted
collection can be designated as EITHER the **matron** or the **sire** in a
given breed call, CryptoKitties-style. Babies can sire and matron, not just
be born — third-generation-and-beyond breeding is in scope by construction,
not a v2 question anymore.

## Ownership rule (who can breed what, who gets the baby)

Adopted directly from real CryptoKitties behavior:

- The caller must **own (or be approved for) the MATRON token** in that
  specific breed call. This is the only ownership check needed.
- The **SIRE** can be (a) a token the caller also owns/is approved for, or
  (b) a token owned by someone else, IF that owner has explicitly listed it
  as publicly available for siring (see Fees).
- The resulting baby **always mints to the matron's owner** — their normal
  wallet, not a TBA. This single rule is what prevents "steal someone else's
  breeding output"; no separate consent flow on the matron side is needed
  beyond the one `ownerOf` check.

## Escalating per-token cooldown (the only anti-farm throttle)

Adopted directly from real CryptoKitties behavior:

- EVERY token that participates in a breed — as matron OR sire — enters a
  cooldown after that breed.
- Each successive cooldown for that SAME token is longer than the last:
  doubling-style escalation, roughly
  1min → 2min → 5min → 10min → 30min → 1hr → 2hr → 4hr → 8hr → 16hr →
  1day → 2day → 4day, capping around 7 days. The exact table is an
  implementation detail, not load-bearing; the escalating-with-use SHAPE is
  the spec requirement. Per-token state: a breed count (cooldown index) and
  a cooldown-end timestamp.
- This is the ONLY throttle. No hard lifetime breed cap, no nested-cap
  (`NESTED_CAP` in the current `BreedingController.sol` is superseded along
  with TBA minting). A token that breeds a lot naturally slows itself down.
- This specifically closes the "freshly-minted baby is an instant
  zero-cooldown matron, breed it again immediately, exponential free supply"
  hole that a flat or zero cooldown would create: a new baby starts at the
  bottom of the ladder, but every use pushes it up the ladder like everyone
  else.

## Sex tag and same-sex fee tier ("test tube babies")

For flavor and a second, orthogonal fee lever (Brady's call, in conversation):

- Every token carries a **sex tag**, `Male` or `Female`, stored on-chain.
  HOODCHAN tokens are `Male` by default; Girlfriends tokens are `Female` by
  default (both fixed, no per-token variance needed for the source
  collections). Every **Baby** is assigned a sex via an independent 50/50
  coin flip at mint time (same seed, one more bit), stored alongside its
  genome so it carries forward into any breed where that baby later
  participates as a parent.
- **Opposite-sex pairing** (the common case) pays the normal birth fee (see
  Fees below).
- **Same-sex pairing** pays a higher birth fee — a flat multiplier (exact
  value TBD/config, not load-bearing to spec) on top of the normal birth
  fee. Flavored in UI copy as "test tube baby" ("science" framing, in
  keeping with the project's tone) — genetics/coin-flip mechanics are
  otherwise IDENTICAL regardless of the parents' sex tags; this is a pricing
  choice only, not a different breeding path.
- This is a cheap addition: one stored attribute per token (fixed for
  HOODCHAN/Girlfriends, coin-flipped once for Babies) and one conditional
  multiplier in the existing fee-calculation step. It does not touch
  ownership, cooldown, allowlist, or genetics logic, and does not reopen any
  bug category from adversarial review.
- A baby produced from a same-sex pairing carries a visible **"Test Tube
  Baby"** badge in its metadata/UI (a boolean derived from
  `matronSex == sireSex` at mint, stored alongside genome) — a cosmetic flex
  trait, not a gene slot, doesn't affect coin-flip inheritance odds at all.
  Surfaced on the baby's detail page and family-tree page as a badge, same
  treatment tier as the mutation/legendary hype callouts.

## Fees (paid by the breed caller, both components in CHAN)

1. **Optional siring fee** — applies ONLY when the sire is NOT owned by the
   caller (borrowing someone else's listed sire). Set by the sire's owner,
   paid to that owner. A token is NOT publicly available as a sire by
   default: its owner must explicitly list it via an explicit boolean opt-in
   (the current `SiringListing.listed` flag pattern is correct — "price 0"
   must never mean "available/free by default").
2. **Flat birth fee** — charged on EVERY breed, no exceptions, including
   breeding two of your own tokens. Small, fixed, owner-configurable (exact
   amount TBD, not load-bearing). Goes to the treasury/fee recipient and
   funds the per-baby OpenAI art-generation cost. Direct CryptoKitties
   precedent (their "autobirth fee"). Multiplied up for same-sex pairings
   per the section above. This is what makes "free and unlimited" not
   actually free — there is always a real cost to producing a baby.

## Breeding flow (single atomic transaction)

One `breed(matronCollection, matronId, sireCollection, sireId)` call:

1. Check matron ownership/approval, sire availability (owned or listed),
   both cooldowns clear, both collections allowlisted, genes available.
2. Write cooldown state for BOTH tokens (before external calls where
   practical).
3. Compute the same-sex/opposite-sex fee tier from both tokens' sex tags;
   collect the birth fee (always, at the applicable tier) and siring fee (if
   borrowing) via SafeERC20 `transferFrom`.
4. Compute seed and genome (and the baby's own sex tag), mint baby to the
   matron's owner, emit event carrying full lineage (both parents, genome,
   seed, sex).
5. Backend generates art (~10–20s) via `breeding-app/lib/breedingImage.ts`
   and sets the baby's tokenURI (existing
   `breeding-app/app/api/breed/[txHash]/route.ts` flow).

**No escrow. No pull-payments. No commit/reveal. No gestation/claim step.**
Genome is computed and revealed in the same tx.

### Accepted tradeoff — stated plainly

The genome seed is deterministically computable from public inputs before
the tx lands. A technically sophisticated caller could simulate the outcome
client-side and choose whether to send the transaction. **This is
explicitly accepted, not mitigated.** Brady's call: "you get what you get."
Do not propose commit/reveal, blockhash anchoring, VRF, or any other
seed-hiding mechanism. (The escalating cooldown + unconditional birth fee
bound the damage: re-rolling costs real CHAN and burns real cooldown time.)

## Genetics

Per-slot inheritance over the 5 gene slots (Hat, Face, Body, Background,
Accessory):

- **50/50 coin flip** between the literal matron and sire trait values for
  each slot independently. NOT numeric-magnitude dominance — the v1
  "numerically higher index wins 60%" rule (still present in
  `GeneticsLib.sol`'s standard branch) made whichever collection occupied
  the higher index band always win, and is superseded. Coin-flip is
  band-agnostic and fixes this.
- **Small mutation chance** and **smaller legendary chance** layered on top
  (the existing sequential-check structure in `GeneticsLib.inheritLocus` is
  a fine skeleton; the branch OUTCOMES change).
- Mutation/legendary values draw from an **off-chain-curated pool** with
  meme-culture flavor. **Implementation constraint (from adversarial
  review):** the pool gets its own explicit reserved on-chain index band per
  slot — it must NOT collide with real trait indices or overflow a slot's
  real range. `traitRegistry.ts` already reserves `248..255`
  (`LEGENDARY_RESERVED_START`); the contract must clamp mutation/legendary
  rolls INTO the reserved band (the current `GeneticsLib` legendary branch
  returning an arbitrary unconstrained byte, and the mutation branch's
  range-arithmetic, both violate this and must change).
- One additional independent coin flip determines the baby's own sex tag
  (see "Sex tag" section above) — not a gene slot, stored alongside the
  genome.

The genome remains the permanent on-chain source of truth (packed uint40 +
stored seed in `HoodchanBabies`); the rendered image is a representation of
it.

## Hygiene requirements (from adversarial review — explicit, still valid)

- **Mint call:** the destination is now an arbitrary caller-side wallet
  (possibly a contract), not a codeless TBA. Make an explicit decision: use
  `_mint` (no `onERC721Received` callback) OR keep `_safeMint` behind
  `nonReentrant`. Do not leave it as an assumption.
- **`nonReentrant` on `breed()`** generally; write cooldown state before any
  external call (CHAN transfer, `genesOf` reads on allowlisted collections)
  wherever practical.
- **Art-generation route:** the public route needs basic rate-limiting/auth
  (`lib/rate-limit.ts` exists in the parent app) regardless of the fee
  throttle — belt and suspenders.
- **Allowlist admin:** additions to `isBreedableCollection` go through the
  same multisig/ownership-guard pattern as the repo's other admin actions.
  A compromised single key adding a malicious contract is a real risk —
  arbitrary `genesOf` return values feed directly into minted genomes.
- **CHAN token verification:** verify CHAN's actual deployed bytecode/
  behavior (plain ERC-20 vs. transfer hooks) before assuming `transferFrom`
  has no reentrancy surface; use SafeERC20 regardless.
- **Chain semantics:** verify Robinhood Chain's actual `block.timestamp` /
  `block.number` behavior empirically before finalizing cooldown durations/
  units — this chain's block-time assumptions already caused one real bug in
  a prior attempt.

## Explicitly cut from scope (do not reintroduce)

- ETH payment path — CHAN-only. (Removes `PayMethod`, `upgradedAllowlist`'s
  ETH-gating role, `pendingEthWithdrawals`, `claimEth`.)
- Mint-into-TBA / nested baby ownership — baby mints straight to the
  matron's owner's own wallet. (TBA nesting remains a thing owners can do
  AFTERWARD, voluntarily, for the existing `lib/leveling.ts` XP — it's just
  no longer part of the breed flow.)
- Commit/reveal (and the whole escrow/lock/expiry machinery it required).

## Engagement features (v1, real product decisions)

- **Hatching-reveal animation** replacing the loading spinner during art
  generation.
- **Mutation/legendary hype treatment** in the reveal UI when a slot rolled
  a mutation or legendary.
- **Family-tree page** — parents, siblings, lineage, read off mint events
  (the `Minted`/`Bred` events already carry both parent ids).
- **Sire XP** — hook siring activity into the existing `lib/leveling.ts`
  XP system IF it's a near-zero-effort wire-up; drop it if not.
